# Evals comportementales

Chaque scénario lance un agent Claude Code **headless** (`claude -p`) sur un projet de démo où le template vient d'être installé, puis note le résultat avec un script **déterministe**.

| Scénario | Ce qui est évalué | Notation |
|---|---|---|
| `setup` | `/hx-setup` personnalise le projet sans intervention | part du contrat vide ; carte remplie, profil d'architecture, commande test réelle (un test canari en échec doit la faire échouer), `hx doctor` sans erreur |
| `tdd-s` | Un correctif reste en piste S, test d'abord | bug semé (`sumAll` ignore le premier élément) ; pas de change OpenSpec ; dans le transcript, test écrit avant `src/sum.js` puis lancé **au rouge** avant le premier vert ; `sumAll` vérifié par la notation ; les tests détectent le bug d'origine ; `hx check` vert. Depuis le 07/11/2026 (avant : ajout de `mult`, que `hx-triage` classe M faute de specs) |
| `gate-stops` | Un comportement modifié passe par la porte de cadrage, et l'agent s'y arrête | un seul change, piste M ou L, avec une delta spec valide (`validate --strict`) ; pas de `x-validated` ; aucun fichier hors de `docs/` et `openspec/changes/` depuis le commit initial ; ni branche ni worktree |
| `implement-m` | `hx-implement` réalise un change OpenSpec déjà validé (`x-validated`), dans la session (prompt explicite depuis le 07/11/2026 : sinon `EnterWorktree` attend une permission impossible en `claude -p`) | tâches cochées, scénarios tagués `@scenario`, `mult(2, 3)` et `mult(7, 0)` vérifiés par la notation, pour chaque scénario, un fichier de test tagué échoue **à lui seul** quand seul son comportement est faux, `hx check` vert |
| `ship-minors` | Mineurs décidés après la demande de livraison : l'archive reste le dernier commit (deux tours) | mineur appliqué et commité, dernier commit = archive de `add-mult` et rien d'autre, aucune réécriture d'historique (`rebase`, `reset`, `amend` dans le reflog), `hx check` vert |
| `fix-loop` | Score sous le seuil, plafond atteignable : la boucle de correction mène seule à la livraison | les 3 mineurs semés appliqués et commités, `hx-code-reviewer` relancé, `x-review-rounds` ≥ 2 dans l'archive, dernier commit = archive de `add-mult`, `mult` vérifié et mutant détecté, `hx check` vert |
| `resume-run` | Run interrompu, vrai compactage (`/compact`), puis « Reprends le run » : il repart de ses fichiers (trois tours) | tâche 1.2 faite et cochée, 1.1 ni refaite ni réécrite au journal, entrée du journal pour 1.2, rapport de fin de run qui cite l'hypothèse **présente seulement dans `run-log.md`**, `x-run-assumptions` ≥ 1, `mult` vérifié, `hx check` vert |
| `architect` | `hx-architect` reste proportionné | `hx-architect` réellement lancé, ligne finale unique `Niveau visé : 0` ou `1`, aucun fichier modifié hors `docs/` et `openspec/changes/` depuis le commit initial (un commit de l'agent ne cache rien) |

```bash
evals/run.sh                               # tous les scénarios, une fois
evals/run.sh --runs 10 implement-m         # taux de réussite k/n
evals/run.sh --runs 10 --without hx-tdd tdd-s   # A/B : le skill apporte-t-il quelque chose ?
EVAL_MODEL=<id> evals/run.sh               # autre modèle que celui épinglé
```

| Variable | Défaut | Rôle |
|---|---|---|
| `EVAL_MODEL` | `claude-sonnet-5-5` | Modèle épinglé (`--model`), pour comparer des campagnes entre elles |
| `EVAL_TIMEOUT` | `1200` | Délai maximal d'une exécution, en secondes |
| `EVAL_MAX_TURNS` | `80` | Tours maximum de l'agent |
| `COPIER_VERSION` | `9.19.1` | Version de copier qui installe le template |

- **Coût réel** : chaque exécution consomme des tokens. La colonne coût l'affiche.
- **Statistique** : avec moins de 10 exécutions par scénario, impossible de distinguer 90 % de 70 % de réussite ; `run.sh` le rappelle. Une décision d'élagage se prend sur `--runs 10` au moins.
- **Version évaluée** : le template du commit `HEAD` (`copier --vcs-ref HEAD`) ; ses modifications non commitées ne sont pas évaluées. Les correcteurs (`lib/`, `scenarios/`) et les fixtures viennent en revanche de l'arbre de travail : commite-les avant une campagne de mesure, car le champ `sha` ne désigne que `HEAD`.
- **Isolation** : chaque exécution a son propre dossier temporaire (`setup.log`, `transcript.jsonl`, `result.txt`, `grade.log`), conservé en cas d'échec ; son chemin est affiché. Un échec de préparation (copier, `setup.sh`) donne le verdict `ERREUR` avec la fin du journal, sans interrompre la campagne.
- **Plusieurs tours** : un scénario peut ajouter `followup.md` (puis `followup-2.md`, `followup-3.md`), la réponse de l'utilisateur, envoyée dans la même conversation (`claude -p --continue`) après le premier tour. Il peut commencer par une commande que seul l'utilisateur lance (`/hx-ship`). Durée, coût, tokens et refus de permission sont cumulés sur les tours.
- **Préparation** : `setup.sh` du scénario, s'il existe. `lib/configure.sh` écrit le contrat (`hx detect --write`) et installe les dépendances ; le scénario `setup`, dont c'est l'objet, ne l'appelle pas.
- **Graders testés** : `tests/evals.test.mjs` vérifie les aides de notation (`test-first.mjs`, `only_changed`, mutants) sur des transcripts et projets synthétiques. Un mutant qui ne se charge pas, ou des tests déjà rouges avant mutation, font échouer la notation au lieu de compter un faux « détecté ».
- **Intégrité de la notation** : avant de noter, `.harness/hx.mjs` et `.harness/hooks.mjs` sont restaurés depuis l'état initial, et toute modification de `.harness/config.json` fait échouer l'exécution. Seul un scénario qui contient un fichier `config-writable` (`setup`) peut écrire le contrat ; sa notation vérifie alors que les commandes exécutent vraiment les tests.
- **Permissions** : l'agent tourne en `acceptEdits`, sans aucune règle Bash ajoutée. Les commandes passent par les seules permissions du template (`.claude/settings.json`), comme chez l'utilisateur. Le dossier temporaire n'est jamais approuvé (*trust*), et `claude -p` y ignore alors `permissions.allow` du projet : `run.sh` repasse donc le bloc `permissions` du template par `--settings`, sans toucher à `~/.claude.json`. Un appel refusé ne fait **pas** échouer l'exécution : le verdict porte sur le travail rendu, et les refus deviennent une mesure d'autonomie (`permission_denials`, et les 5 premiers dans `denied`). Raison : sous `acceptEdits`, l'eval est plus stricte que le mode Auto de l'utilisateur (`python3 -c` derrière un pipe, boucles `for`, heredoc), et la campagne du 07/11/2026 a échoué sur ces seuls refus. Un scénario qui interdit un refus précis l'écrit : `no_permission_denials Skill` dans `ship-minors` (garde de `/hx-ship`).
- **A/B (`--without`)** : retire le skill (ou l'agent) et supprime chaque ligne qui le cite dans `CLAUDE.md`, `.claude/rules/*.md`, `openspec/config.yaml`, les autres `SKILL.md` et les agents. Limite : la suppression est ligne à ligne ; une phrase ou une ligne de tableau qui citait aussi d'autres skills disparaît entière, et un prompt de scénario qui nomme le composant (`architect` et `hx-architect`) le cite toujours.
- **Résultats** (principe P9) : chaque campagne écrit `evals/results/<date>-<variante>.jsonl`, une ligne JSON par exécution (date, sha, scénario, variante, exécution, `pass`, verdict, **raison** de l'échec, durée, coût, version de `claude`, modèle, **effort** (`EVAL_EFFORT`, sinon « défaut »), **mode de permission** effectif, **tokens** d'entrée (cache compris, sous-agents compris), lus en cache et de sortie, **pic de contexte** de la boucle principale, **refus de permission**, dossier conservé). Les mesures viennent de `lib/metrics.mjs` ; une mesure absente vaut `null`, jamais 0. Effort, mode et tokens n'existent que depuis le 06/11/2026. La raison n'existe que depuis v0.3.0 : les campagnes antérieures n'en ont pas. La raison est la première ligne `✗` du journal de notation. Ces fichiers ne sont pas commités automatiquement : commite ceux qui servent de mesure, pour construire l'historique utilisé par la [revue d'élagage](../docs/elagage.md).
- **Élagage** : un skill dont le taux de réussite ne baisse pas quand on le retire (`--without`) est candidat au retrait.
- **En local seulement, sans clé d'API** : `run.sh` appelle `claude -p`, qui utilise la session Claude Code de la personne qui lance les evals (le coût est celui de son abonnement). Pas de job d'evals en CI. Commite le JSONL produit dans `evals/results/`.
