01 — En bref

Quatre idées tiennent toute la charpente

Le harness ne remplace ni Claude Code ni OpenSpec : il les assemble en un processus outillé, vérifiable et proportionné au besoin.

Quoi

Une couche de harness autour d’OpenSpec : skills, agents, rules, hooks, contrôles CI.

Agnostique

Le générique ignore la stack. Le spécifique tient dans quelques fichiers remplis par /hx-setup.

Copier

Installe et met à jour les projets par fusion à 3 voies. Tes personnalisations restent.

Règle d’or

Tout contrôle existe en CI. Les hooks locaux ne font qu’accélérer le retour.

02 — Cycle de vie

Un template qui descend, des leçons qui remontent

Le repo Harness est versionné par tags. Chaque projet le reçoit par Copier, l’adapte une fois à sa stack, puis suit ses mises à jour. Ce qui s’apprend sur le terrain remonte dans le template.

  1. Détecter les manifestes
  2. Proposer composants et commandes
  3. Exécuter chaque commande (preuve)
  4. Rédiger rules, carte, setup CI
  5. Valider : tu relis le diff

03 — Le workflow

Un seul arrêt prévu : la porte de cadrage

Tu cadres avec l’agent jusqu’à une spec qui dit ce que tu as demandé. Ensuite le run va seul jusqu’au rapport, dans son propre worktree, pendant que tu cadres le change suivant.

  • skill
  • sous-agents
  • registre OpenSpec / template
  • optionnel

04 — Pistes

Le processus a la taille du changement

hx-triage choisit la piste avant toute ligne de code. Un correctif d’une ligne n’a pas besoin de spec ; une décision structurante a besoin d’un ADR.

S

Correctif

Petit, local, réversible.

  • pas de spec
  • hx-tdd ou hx-debug
  • hx-verify puis commit
M

Fonctionnalité

Le cas courant.

  • spec OpenSpec, design optionnel
  • porte de cadrage, puis run en worktree
  • hx-review, /hx-ship
L

Structurant

Difficile à défaire.

  • spec + design requis
  • hx-architect et ADR (hx-adr)
  • validés à la porte de cadrage

06 — Hooks

Des garde-fous le long de la session

Quatre points d’accroche, du démarrage jusqu’au moment où l’agent rend la main. Ils raccourcissent la boucle de retour ; la CI reste l’arbitre.

SessionStart

Contexte de session. Installe la CLI OpenSpec si elle manque.

PreToolUse

Confirmation avant d’écrire une spec principale ou un fichier qui décide de ce qui s’exécute.

PostToolUse

Lint du fichier qui vient d’être édité.

Stop

D’après git : contrôles rapides des composants modifiés, chemins protégés signalés.

règle d’orTout contrôle existe en CI. Les hooks locaux ne font qu’accélérer le retour.

07 — Contrôles

hx check, brique par brique

Les mêmes commandes tournent en local et dans la CI (hx-check.yml). Une règle importante devient un contrôle déterministe, pas un paragraphe de prose.

  1. contratconfig.json valide
  2. openspecvalidatefast
  3. archiveschanges archivés
  4. pistesS · M · L respectées
  5. tracescénario ↔ @scenario
  6. lintpar composantfast
  7. typecheckpar composantfast
  8. archrègles de dépendance
  9. testjamais vert sans test
  • 1
    Jamais vert sans testUn projet sans test exécuté ne passe pas : la tour n’a pas de sommet.
  • 2
    Traçabilitéhx trace relie chaque scénario OpenSpec à un test tagué @scenario.
  • 3
    Mode rapidehx check --fast : validate OpenSpec, lint et typecheck. Ce que les hooks lancent en cours de route.
  • 4
    Multi-stackChaque commande s’exécute dans le dossier de son composant : api en .NET, web en Node…

08 — Générique / spécifique

Le cœur de l’agnosticité

Ce qui vient du template est mis à jour par copier update. Ce qui décrit ta stack est écrit une fois par /hx-setup et n’est jamais écrasé. Entre les deux, une seule interface.

Générique

Vient du template, s’améliore dans Harness.

  • CLAUDE.md
  • .claude/skills · agents · rules
  • .claude/settings.json
  • .harness/hx.mjs · hooks.mjs
  • openspec/config.yaml
  • .github/workflows/hx-check.yml

Le contrat

.harness/config.json : la seule interface entre le harness et la stack.

// un composant par stack
"api": {
  "path": "src/Api",
  "commands": { "test": "dotnet test" }
},
"web": {
  "path": "web",
  "commands": { "lint": "npm run lint" }
}

Spécifique

Rempli par /hx-setup, jamais écrasé.

  • .harness/config.json
  • .harness/project.md
  • .harness/ci/setup/action.yml
  • .claude/rules/stack-*.md
  • .github/dependabot.yml
  • .github/CODEOWNERS

09 — Principes

Onze règles de chantier

Chacune a une conséquence concrète dans le template. Un composant qui ne prouve pas son gain est retiré (élagage).

  1. Générique / spécifique séparésLes skills n’écrivent jamais npm ou dotnet : ils passent par hx run.
  2. OpenSpec, registre de l’intentionÉtendu sans fork : config.yaml, clés x-*, CI.
  3. Contrôles déterministes > proseUne règle importante devient un lint, un test ou un check.
  4. Le contexte est un budgetCLAUDE.md est une carte (≤ 100 lignes) ; rules ciblées par chemin.
  5. Qui produit n’évalue pasLes reviewers sont des sous-agents indépendants.
  6. Pas de « terminé » sans preuvehx-verify exige une sortie de commande fraîche.
  7. Processus proportionnéPistes S / M / L : un correctif n’a pas besoin de spec.
  8. Boucle de pilotageUne erreur récurrente devient rule, contrôle ou skill.
  9. ÉlaguerUn composant sans gain mesurable est retiré.
  10. Architecture proportionnéeFeature-first ; une couche seulement pour un besoin nommé.
  11. Standard quand c’est gratuitSkills au format SKILL.md, portables vers un autre outil.

10 — Installer

Trois commandes, une demi-heure

Prérequis : git et Node ≥ 20.19. Dans un dossier vide ou un dépôt git propre, nouveau projet ou existant.

1 min01

Installer

npx github:PatayEnCroute/Harness

Vérifie git, installe uv au besoin, lance Copier, ouvre Claude Code Desktop.

10–20 min02

Personnaliser

/hx-setup

Détecte la stack, vérifie chaque commande en l’exécutant, finit par hx doctor.

1 min03

Mettre à jour

uvx copier@9.19.1 update --trust

Fusion à 3 voies. Le spécifique n’est jamais réécrit ; hx migrate ajoute les clés nouvelles.

Par un agent : dis à Claude Code « Installe le harness github.com/PatayEnCroute/Harness en suivant son INSTALL.md ».
